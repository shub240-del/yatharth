# Yatharth V0.2 validation report — 2026-10-05

## 1. Decision

**A — technically functional** is supported for the tested local workflow. **B — internally validated** is not justified as a broad detection-quality claim: an internal evaluation exists, but it reveals major gaps. **C — externally validated** is not achieved. **D — detection effectiveness not yet validated for intended family-safety use** is the appropriate reliability conclusion. Do not describe this prototype as ready to protect families.

## 2. Scope and architecture

V0.2 adds evaluation, review tooling, regression expectations, and documentation. OpenWorker core remains unmodified; no upstream code is vendored. Yatharth independently owns identity, family membership, consent, domain signals, risk decisions, alerts, retention and audit. Optional provider machinery supplies schema-validated evidence only. Standalone SQLite operation needs neither OpenWorker nor model keys. research/openworker-assessment.md records the earlier pinned upstream inspection and exact adapter boundary; no new upstream compatibility verification is claimed.

## 13. Ten decision questions

1. **Is detection reliable?** Not established; the synthetic challenge misses96/161 serious cases.
2. **Where does it fail?** Hindi/Hinglish, paraphrases/obfuscation, implicit evidence, and educational quotation/negation. Marathi coverage is insufficient.
3. **Does it beat simple keywords?** On precision and FPR here, yes; on recall and F1, no. There is no overall superiority claim.
4. **Does AI improve it?** Unknown: no live comparison. The existing bounded adapter cannot repair most missing signals.
5. **How many false positives?**2/75 nonserious examples, FPR2.67%; both are benign English warnings. Operational rates remain unknown.
6. **How many false negatives?**96/161 proposed serious examples, miss rate59.63%; dangerous misses dominate.
7. **Does it work across languages?** The matched serious recall is88.46% English,0% Hindi,3.85% Hinglish. Multilingual readiness is unsupported.
8. **Highest-value improvement?** Language-aware contextual evidence extraction. First establish two-reviewer multilingual labels and a separate untouched holdout; compare the candidate at an agreed false-alert budget before changing product behavior.
9. **Ready for controlled user testing?** Suitable for supervised synthetic usability and annotation exercises. A real-message study would need its own consent, data-handling and evaluation design; protective reliance or autonomous escalation is not supported by these results.
10. **What should not be built next?** WhatsApp/GPS/wearable/health/emergency integrations, autonomous interventions, broader data collection, or an OpenWorker fork. They do not resolve the measured detection gap.

## 14. Next evaluation gate

Have two independent qualified reviewers label the existing packets by language; retain disagreements as ambiguous and measure coverage/agreement. Define a separate frozen holdout sourced and reviewed independently, decide acceptance criteria before scoring, and evaluate a language-aware contextual candidate against both keyword baselines at the same false-alert budget. Measure severity, subgroup recall, errors, and provider failure/latency/cost if AI is actually enabled. This is proposed follow-up work, not completed external validation.
